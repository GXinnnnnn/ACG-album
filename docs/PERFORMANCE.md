# 性能实测与复现

本页记录 ACG-album 的源码 worker 实测，帮助区分资料库启动、本地文件索引、页面查询、在线资料匹配和缩略图生成。2026-10-26 的测量对应已发布 1.0.1 的实现，原始结果继续保留；2026-10-27 的导入预览与缩略图数据对应后续源码优化，尚未替换 GitHub 安装包。耗时仅对应下述环境与用例，不作为任意图库的速度保证。

## 测试环境与计时范围

- 日期：2026-10-26。
- 平台：Windows x64，Intel Core i5-12400，32 GB RAM。
- 运行时：Node.js 24.21.0，SQLite 3.53.4；从源码启动独立 worker。
- 启动用例：直接生成 100,000 条媒体 SQL 记录，媒体元数据状态预设为 `ready`，不读取或解码 10 万张真实图片。
- 索引用例：在临时目录创建占位文件，关闭在线匹配并抑制后台媒体解码，单独测量目录枚举与数据库写入。

`ready` 从创建 worker 计时到收到其就绪事件；`init` 是就绪后的初始化 RPC。两者不包含 Electron 窗口首次绘制、界面动画、缩略图生成或真实网络请求。实验没有控制系统文件缓存，样本量也不足以给出统计上的稳定加速倍数。

## 已有资料库的重复启动

对照组在同一份源码树中，通过测试脚本的内存替换重现原先每次启动重复执行迁移工作的行为，并恢复旧的根目录查询；改进组使用一次性迁移门控和限定文件夹类型的根目录查询。**这是一组隔离行为对照，不是两个历史安装包的整机对比。**

| 测量项目                      | 旧启动行为重现        | 当前实现             |
| ----------------------------- | --------------------- | -------------------- |
| 已有库 `ready`，连续三次，ms  | 792.7 / 469.3 / 427.5 | 101.7 / 103.9 / 88.6 |
| 上述三次 `init` 范围，ms      | 42.0–52.1             | 19.4–22.0            |
| 根目录查询，单次 SQL 剖析，ms | 27.53                 | 0.15                 |
| 新建空库 `ready`，单次，ms    | 239.6                 | 281.9                |

本轮可观察的改善集中在已有资料库的重复启动；新建空库的单次结果没有显示提速。迁移与修复仍会在需要时执行，完成后记录版本，避免下次启动重复更新整张表。

独立迁移回归另外使用纯 SQL 生成 10 万条旧排序键记录，名称为 JPG / MP4 各半，不创建 10 万个媒体文件：最终排序回归测得含首次迁移的 worker 就绪约 5.592 秒。另有回归确认完成的迁移不会在第二次启动重复执行，并覆盖了中断回滚后重试，以及保留人工整理结果与待处理队列的检查。

## 本地索引与页面查询

仓库另有 [十万文件索引回归](../tests/indexing.test.cjs)，会真实创建 10 万个空 JPG 文件，用于验证扫描期间仍可查询、搜索、取消与有界清理。这与本页启动和排序用例的 SQL 合成记录是不同夹具，也不测量真实图片解码。最终该十万文件用例已完成全流程，并与目录排序、启动、SQLite checkpoint 回归一同通过，共 26 项。大子树清理改为按节点行号（`nodes.rowid`）顺序分批处理，保留每 128 条让出执行机会与 `synchronous=FULL`。

原始启动报告附带的索引用例是 **4,000 个占位文件、20 个一级相册**，另有一个根目录；初次索引为 882.4 ms 与 880.9 ms。两份报告使用同一套索引逻辑，启动对照开关不切换历史索引实现。这组结果不用于宣称索引提速。占位文件不包含可正常解码的媒体内容，计时也抑制了后台解码。

另一组索引对照包含 **4,000 个独立一级目录，每个目录一个微小 MP4 占位文件**，共 8,001 个节点（4,001 个文件夹与 4,000 个视频条目）。在线匹配关闭，后台媒体解码被抑制；两组都已使用启动迁移门控。结果取自 `index-4000-albums-before.json` 与 `index-4000-albums-after.json`：

| 扫描阶段 | 索引优化前                | 索引优化后                |
| -------- | ------------------------- | ------------------------- |
| 初次扫描 | 40.55 秒，98.652 目录/秒  | 26.13 秒，153.095 目录/秒 |
| 复扫     | 24.70 秒，161.967 目录/秒 | 13.07 秒，305.989 目录/秒 |

该改动在目录汇总值未变化时避免重写排序索引，并用单目录的短同步事务合并封面指针与汇总写入；异步工作留在事务外，SQLite 仍使用 `synchronous=FULL`。这是一组特定目录形态的顺序实测，未控制磁盘缓存，也没有真实视频解码或联网匹配。索引优化前的数据是修改前实测归档，启动脚本的 `ACG_PERF_BASELINE=1` **不能回滚索引实现**。

10 万条合成媒体记录的末页查询分别覆盖名称、创建日期、修改日期、大小四种排序的升序与降序，共八次 RPC，每页 50 条。当前启动报告测得 13.9–59.1 ms。最终独立旧键迁移回归的八次末页 RPC 为 25–76 ms，均通过单次严格小于 2,000 ms 的检查。它们是数据库查询与 worker 通信耗时，不包括图片加载和界面呈现。

## 在线匹配与缓存

在线匹配处理一级作品 / 角色文件夹，本地扫描计数则可能包含大量媒体文件，两者需要分别统计。Bangumi JSON API 资料请求仍按至少约 **1,050 ms** 的间隔串行发出，长期节奏约为 **0.952 次 API 请求/秒**，并保留限流退避；封面 CDN 下载不使用此间隔，另受传输与本地处理耗时影响。一个相册可能涉及名称搜索、条目详情、人物列表与封面下载，不能直接用“每秒请求数”换算“每秒完整相册数”。已命中本地资料或有效请求缓存的相册可以减少在线请求。

受控假网络回归记录了以下行为：

- 1,000 个不同名称的一级相册产生 1,000 次搜索，待处理队列不超过 64。假网络与虚拟计时器的墙钟耗时为 14.119 秒，但模拟的请求间隔累计至少 1,048.95 秒；**14.119 秒不能当作真实 Bangumi 同步速度**。
- 三个同名相册共用请求缓存，搜索、详情、人物和封面各请求一次，共 3 次 JSON API 请求与 1 次 CDN 封面请求；重启后再导入已有有效缓存的相册，HTTP 请求数为零。

缓存结果取决于名称、条目、有效期与账号访问范围。上述回归不访问真实网络，也没有测量 Bangumi 服务在不同网络、账号或限流状态下的吞吐。

## 批量缩略图与首次导入预览（2026-10-27）

首次扫描会为尚无封面的相册发布临时本地图，不再等待整个子树及在线匹配结束。扫描批次发现图片便更新空封面；进入较大的子相册前，还会对同批兄弟目录做有界预览探测。每次最多检查 128 个目录项、8 个目录、4 层，不跟随符号链接。最终封面仍按作品 / 角色的自然名首图、普通照片的最新图片规则选择，已选的人工封面与有效 Bangumi 封面继续保留。超出预览预算的目录会在正常扫描发现图片时补上封面。

只读比较 8 个真实目录，共 1,334 个目录项 / 1,218 张图：最早可用图读取 12 个目录项、8 次 stat，约 8.810 ms；自然名最小需枚举全部目录项、8 次 stat，约 11.605 ms；最新图需枚举全部目录项并 stat 全部图片，约 18.621 ms。因此临时预览采用最早枚举到的可用图，不为预览完整枚举及读取每张图的时间。该单次暖盘毫秒测量存在噪声；更可靠的差异是枚举 / stat 的数量。首次自然排序键初始化另需约 78.153 ms，未混入选择时间。复现：`node scripts/bench-import-cover.cjs`。

缩略图使用四条有界生成通道和 `quality:86, alphaQuality:100, effort:1`，保持原有输出尺寸与 10 GB 缓存上限。卡片按实际列宽与屏幕 DPR 一次请求所需尺寸，可视区域的生成任务优先于预加载区域。

只读采样 `D:\\游戏图片` 中 24 张真实图片（7 JPEG、7 PNG、7 GIF 首帧、3 WebP，12 张带透明通道；像素中位约 1.04 MP，最大 8.29 MP），各组合共跑两轮（正序、反序各一轮），以下取两轮中位数。计时是预热源文件后**前 15 个请求全部生成完成**，输出留在内存，不含缓存落盘、SQLite、IPC 和浏览器绘制。

| 生成尺寸 | 旧配置：并发 2 / effort 4 | 新配置：并发 4 / effort 1 |
| -------- | ------------------------- | ------------------------- |
| 512      | 398.87 ms                 | 169.31 ms                 |
| 768      | 567.96 ms                 | 217.64 ms                 |
| 1024     | 702.43 ms                 | 248.80 ms                 |

相同 quality / alphaQuality 下，本样本 RGB PSNR 接近，透明通道误差为零；新编码的缓存体积增加约 15%–16%。另测 `quality:82` 可以把体积降回旧基线附近，但 PSNR 下降约 0.60–0.62 dB，768 / 1024 档没有额外速度收益，因而没有采用。样本按格式均衡选择，未按全盘频率加权，结果不代表任意图库或 160 MP 极端输入。复现：

```powershell
node scripts/bench-thumbnails.cjs --count 24 --tiers 512,768,1024 --rounds 2
```

## 复现方式

先按仓库开发说明安装依赖，并使用支持内置 `node:sqlite` 的 Node.js；本页记录的运行时为 24.21.0。运行 [启动性能脚本](../scripts/check-startup-performance.cjs) 可自行生成环境、三次启动、SQL 剖析、本地索引与八种末页 RPC 的 JSON 报告。脚本创建并清理临时用例目录，不使用个人图库或 Token。

```powershell
$env:ACG_PERF_ROWS = '100000'
$env:ACG_PERF_FILES = '4000'
$env:ACG_PERF_FILES_PER_ALBUM = '200'
$env:ACG_PERF_BASELINE = '1'
$env:ACG_PERF_OUTPUT = 'artifacts/startup-performance-before.json'
node scripts/check-startup-performance.cjs

$env:ACG_PERF_BASELINE = '0'
$env:ACG_PERF_OUTPUT = 'artifacts/startup-performance-after.json'
node scripts/check-startup-performance.cjs

node --test tests/startup-performance.test.cjs
```

复现 4,000 个一级目录的当前索引结果时，另行使用下述夹具形态。`ACG_PERF_ROWS=1000` 仅缩小该次脚本附带的启动 / RPC SQL 夹具，文件索引仍然是 4,000 个目录与 4,000 个占位文件。

```powershell
$env:ACG_PERF_ROWS = '1000'
$env:ACG_PERF_FILES = '4000'
$env:ACG_PERF_FILES_PER_ALBUM = '1'
$env:ACG_PERF_BASELINE = '0'
$env:ACG_PERF_OUTPUT = 'artifacts/index-4000-albums-after.json'
node scripts/check-startup-performance.cjs
```

旧键迁移与大目录排序回归位于 [目录排序测试](../tests/directory-sort.test.cjs)：

```powershell
node --test tests/directory-sort.test.cjs
```

`ACG_PERF_BASELINE=1` 仅在测试 worker 的内存源码中重现旧启动行为，不修改应用源文件。`ACG_PERF_FILES_PER_ALBUM` 决定索引夹具的目录形态，比较结果时需要保持一致。原始 `startup-performance-before.json` 与 `startup-performance-after.json` 已作为本次验收归档；本页取其中可复现的摘要，完整报告由脚本生成。

实测应串行进行，记录当时的提交、运行时、磁盘和后台负载。以上数据未覆盖首次真实大图库解码、百万真实图片、安装包启动时间或 4K 帧率；这些场景需要各自的媒体样本与独立计时。
